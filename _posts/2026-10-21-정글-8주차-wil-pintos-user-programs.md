## 이번 주 목표

- 문제해결
  - 목표: 테스트 케이스와 문서에 있는 요구사항만 읽고 문제 해결하기
    - 결과: 70% (요구사항은 이해했으나 구현의 시작점과 필요한 상태를 스스로 도출하는 것이 어렵다.)
- 설계
  - 목표: 파일별로 구현할 체크리스트 만들기
    - 결과: 70% (수정할 파일과 함수별로 할 일을 정리했다. 다만 여러 기능이 연결되는 부분에서는 설계에 많은 시간이 필요했다.)
- 구현
  - 목표: 체크리스트를 보고 C언어로 구현
    - 결과: 90% (구체적인 설계가 주어지면 구현할 수 있었으나, 자료구조와 메모리 수명 판단에는 추가 학습이 필요하다.)
- 품질
  - 목표: 버그로 인한 재작업을 줄이는 코드 작성
    - 결과: 70% (PR을 올렸을 때 여러 부분에서 놓친 것들이 많았다.)
- 유지보수
  - 목표: 읽기 쉬운 코드와 이해를 돕는 주석 달기
    - 결과: 80% (한 함수에 여러 책임이 모이는 부분은 더 개선할 필요가 있다.)
- 협업
  - 목표: 팀원과 자주 소통하여 진행 상황 공유
    - 결과: 90% (매일 주기적으로 진행 상황을 점검했다.)
- 태도
  - 목표: AI에게 정답을 요구하지 않고 문제해결
    - 결과: 70% (직접 구현하려고 노력했지만, 후반에 복잡한 내용이 나오면서 어디부터 시작해야 할지 AI에게 물어보게 됐다.)
- 비즈니스 이해
  - 목표: 요구사항 분석 또는 테스트 요구사항 이해
    - 결과: 80% (테스트가 기대하는 동작은 어느 정도 이해했다. 하지만 동작을 설계하는 것은 별개였다.)
- AI 활용
  - 목표: 문서 작성이나 메모에 AI 활용. 단, 정답은 금지
    - 결과: 70% (메모를 작성하는 데에는 유용하게 썼지만 공부에는 그닥 잘 활용하지 못한 것 같다.)
- 학습 민첩성
  - 목표: 배운 개념을 구현에 응용할 수 있도록 하기
    - 결과: 70% (개념을 읽으면 이해되는 느낌은 있었지만 실제 코드로 옮기는 첫 단계가 어려웠다.)

## 시도한 접근 방식

- 전체 실행 흐름을 먼저 살펴봤다.
  - 사용자 프로그램 로딩, 인자 전달, 사용자 모드 실행, 시스템 콜, 종료와 자원 정리의 흐름을 기준으로 각 기능의 역할을 연결하려고 했다.
- 수정할 파일과 함수별로 체크리스트를 작성했다.
  - `process.c`, `syscall.c`, `thread.h` 등에서 필요한 변경을 나누고, 구체적인 작업으로 적었다.
  - 체크리스트가 구체적일수록 구현은 수월했지만, 체크리스트 자체를 만드는 과정에서 개념 이해가 부족한 부분이 드러났다.
- 테스트 결과와 실행 흐름을 함께 확인했다.
  - 통과 여부뿐 아니라 시각화 도구에서 프로세스 상태와 자원 정리 시점을 살펴봤다.
  - 실패한 지점만 보는 것보다 그 전에 어떤 순서로 실행됐는지 확인하는 것이 원인을 찾는 데 도움이 됐다.

## 학습 과정에서 겪은 어려움

### 1. 요구사항을 이해해도 구현을 시작하기 어려웠다.

- 공식 문서와 테스트 코드를 읽고 어떤 동작이 필요한지는 이해할 수 있었다.
- 하지만 실제로 어떤 자료구조가 필요하고, 어느 함수부터 수정해야 할지 스스로 판단하는 데 많은 시간이 걸렸다.
- 반면 함수별로 해야 할 일이 체크리스트에 구체적으로 정리된 이후에는 구현이 비교적 수월했다.
- 이를 통해 문제의 요구사항을 이해하는 것과 구현 가능한 작업으로 나누는 것은 별개의 능력이라는 점을 느꼈다.

### 2. 개별 기능보다 기능 간 관계를 이해하는 것이 어려웠다.

- 각 함수의 역할을 이해하더라도 여러 함수가 연결되어 실행될 때 어떤 상태가 변하는지 파악하기 어려웠다.
- 특히 부모·자식 프로세스의 관계, 자원 정리, 동기화처럼 여러 기능에 걸친 문제에서는 설계에 많은 시간이 필요했다.
- 함수 하나의 동작에 집중하기보다 전체 실행 흐름에서 해당 함수가 어떤 역할을 하는지 함께 확인해야 한다고 느꼈다.

### 3. 테스트를 분석하는 방법이 익숙하지 않았다.

- `args-single` 테스트 코드를 찾는 과정에서 테스트 이름과 실제 소스 파일이 반드시 일치하지는 않는다는 것을 알게 됐다.
- 테스트 코드를 읽기 전에 어떤 파일이 실행되고, 어떤 입력이 주어지며, 어떤 결과를 검사하는지 파악하는 과정도 필요했다.
- 앞으로는 테스트 이름만 보고 소스 파일을 찾기보다 빌드 설정과 검증 스크립트를 함께 확인하려고 한다.

## 새롭게 배운 점

- 요구사항을 읽은 뒤 바로 구현하기보다, 필요한 상태와 함수의 역할을 먼저 정리하는 것이 효율적이다.
  - 무엇을 구현해야 하는지 이해했더라도, 필요한 자료구조와 함수별 책임이 정해지지 않으면 코드를 작성하기 어려웠다.
  - 다음에는 입력, 출력, 필요한 상태, 실패 조건을 먼저 정리하고 이를 구현 체크리스트로 옮기려고 한다.

- 함수를 개별적으로 이해하는 것뿐 아니라 전체 실행 흐름 속에서 이해해야 한다.
  - 한 함수의 코드만 읽으면 정상적으로 보이더라도 다른 함수와 연결되면서 예상하지 못한 문제가 발생할 수 있었다.
  - 앞으로는 관련 함수의 호출 관계와 실행 순서, 상태가 변하는 시점을 함께 확인하려고 한다.

- 테스트를 통과하는 것과 구현의 정확성을 확인하는 것은 다르다.
  - 테스트 통과 여부만으로는 자원 정리나 실행 순서에 문제가 없는지 확신하기 어려웠다.
  - 정상 동작뿐 아니라 실패하거나 실행 순서가 달라지는 상황도 고려하면서 테스트해야 한다는 점을 배웠다.

- 막혔을 때 무작정 코드를 수정하기보다 모르는 부분을 구체적으로 정리하는 것이 중요하다.
  - 구현이 막히면 문제의 원인이 개념 이해 부족인지, 코드의 실행 흐름을 파악하지 못한 것인지 구분하기 어려웠다.
  - 앞으로는 기대한 동작과 실제 동작, 관련 함수, 의심되는 원인을 먼저 적고 하나씩 확인하려고 한다.

- AI에게 자신의 생각을 검증하는 용도로 활용하는 것이 학습에 도움이 될 것 같다.
