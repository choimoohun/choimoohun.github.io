## 시도한 접근 방식

단순히 버그만 잡는 것이 아니라 코드를 읽고 파악하는 것을 목표로 잡고 문제에 접근하는 것이 좋겠다고 생각했다. 적절한 결과를 출력할 수 있도록 수정해야 할텐데 만약 정말 버그만 잡아버리면 이런 상황이 될 것 같다: ![100x100_safe](/assets/100x100_safe.png){: .normal }

따라서 문제의 주석을 참고하여 Thinking Point와 디버그 메모를 남겨두었다. 20문제 중 15문제에 대한 메모를 작성했다. 메모에는 각각 '증상', '확인 과정', '원인과 해결', '배운 점' 등을 나누어 문서처럼 작성했다.

### 증상

```c
static void image_fill(Image *img, unsigned char value) {

    size_t total = (size_t)img->width * (size_t)img->height * (size_t)img->channels;
    for (size_t i = 0; i < total; i++) {
        img->px[i] = value;
    }
}
```

`img->px[i] = value`에서 `Exception has occurred. Segmentation fault` 발생

### 확인 과정

디버깅을 통해 의심되는 값을 찾아보았다. `total`의 값은 `17179869184`, `size_t` 자료형이므로 x64 환경에서는 `unsigned long long`의 크기와 같다. 범위는 1,844경 정도 되며 그에 반해 `unsigned int`는 42억 정도 된다. 그런데 반해 `img->nbytes`의 값은 0이 되어 있었다. 이 시점에서 이미 반복문은 `img->px[i]`의 범위를 넘어섰다. `i`가 `134464`이 되고 나서야 비로소 크래시가 발생했다.

### 원인과 해결

원인은 `img->nbytes`에 있었고 `width * height * channels`의 값이 `total`과 동일한 값이 나와야 하지만 `signed int`의 범위가 21억까지인 것을 생각해보면 한 바퀴 돌아 0이 되어버린다.

이를 해결하려면 우선 타입부터 바꿔야 한다.

1. 구조체의 `nbytes`의 타입을 `size_t`로 바꾼다.
2. `width * height` 곱셈이 `SIZE_MAX`를 넘는지 확인하고 그 결과 값과 `channels`와의 곱셈이 `SIZE_MAX`를 넘어서는지 검사한다.
3. 연산할 때 `size_t`로 캐스팅하는 것을 잊지 않는다.

### 배운 점

- 곱셈 오버플로우는 `num1 > MAX_VALUE / num2` 혹은 `num1 < MIN_VALUE / num2`처럼 검사할 수 있다.
- `size_t`의 범위가 넓더라도 곱셈마다 검사를 해주자.

---

추가로 흥미로운 점을 발견했는데 `img->px = malloc((size_t)img->nbytes);`에서 할당된 메모리는 0이다. 그러나 C언어에서는 경계를 크게 벗어나지 않는 이상 곧바로 크래시가 나지 않고, `img->px[i]`에서 `i`가 134,464까지 증가할 때까지 반복문이 계속 되었다. 그렇다면 왜 i가 일정 값에 도달했을 때 크래시가 발생했을까?

- `malloc(0)`으로 반환받은 포인터는 접근할 수 있는 유효한 배열을 제공하지 않는다. `px[0]`부터 이미 잘못된 접근이었던 것이다.
- 운영체제는 C 객체의 경계를 검사하지 않기 때문에, 힙에 매핑된 다른 메모리를 덮어쓰는 동안에도 크래시가 발생하지 않았던 것이다.
- 이번에는 힙 매핑의 끝에서 크래시가 났지만, 메모리 배치가 달라지면 크래시가 발생하는 위치도 달라질 수 있다.
- 이번 문제는 65,536 × 65,536라는 크기로 인해 RGB나 RGBA 둘 다 오버플로우가 날 수 밖에 없으나 좀 더 적은 픽셀 수였다면 RGB의 경우엔 `가로 x 세로 x 3`, RGBA의 경우 `가로 x 세로 x 4`이기 때문에 후자가 `int`의 최대값에 더 빨리 도달할 것이다.

## 문제와 해결 과정

원인을 찾았을 때 해결 방법까지 알아내면 좋겠지만 아쉽게도 완전히 C에 익숙해진 것은 아닌지 코드를 수정하는 단계에서 막힐 때도 있었고, 크래시를 해결했지만 뭔가 아쉬운 기분이 들 때도 있었다. 그런 경우 AI의 도움을 받아 수정한 코드를 검증해보았다.

```c
static int conn_open(Conn *c, size_t bufsz) {
  // 문제 18번 中 처음 수정했던 코드
    ...

    if (!handshake_ok(c)) {

        // free(c->tx); // ??
        goto fail_tx;
    }

    return 0;

fail_state:
    free(c->state);
fail_tx:
    free(c->tx);
fail_rx:
    free(c->rx);
    return -1;
}
```

당연히 코드의 흐름을 보고 미리 해제하는 부분을 주석으로 지워놓고 `goto fail_tx;`로 건너뛰어 밑에서 해제할 수 있도록 유도를 했으나 이는 잘못된 방법이라고 한다. `fail_tx`가 아닌 `fail_state`로 이동하여 위에서부터 모든 해제가 이루어지도록 해야한다.

이런 식으로 문제를 해결하지 못하거나 혹은 해결을 했더라도 AI에게 검증을 요청하여 올바르게 수정한 것인지 확인하고 틀린 부분을 메모해두었다. 생각보다 쉬운 문제라서 금방 풀었다고 생각했는데 알고보니 올바르게 수정하지 못한 문제들이 많았다. 코드를 좀 더 주의 깊게 살펴봐야겠다.

## 새롭게 배운 점

- C언어는 생각보다 문제의 원인을 쉽게 알려주지 않는다. `Aborted` 아니면 `Segmentation Fault`만 알려주고 꺼진다.
- 문제의 원인을 알려면 코드를 읽고 메모리의 할당/해제가 어디서 일어나는지 파악해야 한다.
- 가장 최근에 해제된 메모리를 다시 할당받아 사용할 수 있기 때문에 크래시에 유의해야 한다.
- `strchr()`나 `strdup()` 등 생소한 함수들의 존재를 알게 됐다.
- 디버거를 잘 활용하지 않았었는데 이번 기회에 어느 정도 응용해볼 수 있었다. 특히 `watch`, `step`과 같은 명령어는 vscode에서 대신 GUI로 사용할 수 있게 해주기 때문에 더 쉽게 디버깅할 수 있다.
- **메모리를 16GiB 할당하려고 하면 진짜 16GiB를 할당한다!** ~~내 노트북 램이 32GB라 살았다.~~
